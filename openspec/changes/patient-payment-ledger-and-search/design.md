## Context

Cabinet Nour El Islam operates with a high volume of physical therapy sessions. Currently, session treatment costs and patient cash payments are coupled into the `session` table (`cost`, `paidAmount`). In daily operations, patients frequently deposit lump sums (e.g., 2,000 DA) covering a current 500 DA session plus future sessions as advance credit (1,500 DA).

When patients return for subsequent sessions, the existing UI forces workers into a dilemma:
1. Entering 0 DA flags the session as red "IMPAYÉ", causing disputes with patients who already paid.
2. Entering 500 DA falsifies the daily cash register by recording 500 DA that never entered the physical cash drawer and inflates patient payment totals.

Additionally, assigning a patient to a session requires scrolling through an unindexed, plain `ComboBox`, creating friction and homonym confusion.

## Goals / Non-Goals

**Goals:**
- **Decoupled Financial Architecture**: Separate treatment billing (`session.cost`, `therapyPlan.cost`) from physical cash collection (`payment` ledger).
- **Append-Only Ledger**: Treat payments as immutable records. Never delete or update payment records; handle corrections through auditable reversals (`REVERSAL`) and refunds (`REFUND`).
- **Zero-Friction Session UI**: Ask workers one simple question: *"How much cash was actually received today?"*, automatically defaulting to 0 DA if covered by credit, with live financial preview.
- **Derived Session Status**: Dynamically compute visual badges (e.g., `RÉGLÉ`, `COUVERT PAR AVANCE`, `IMPAYÉ`) based on the patient's running coverage rather than fragile stored flags.
- **Space-Insensitive Keyboard Search**: Real-time filtering of patients by name or phone digits, displaying live balance badges and enabling selection via keyboard navigation.
- **Zero Data Loss**: Migrate existing `session.paidAmount` and `therapyPlan.cost` records idempotently into the ledger without altering historical totals or balances.

**Non-Goals:**
- Multi-currency support (standardized on Algerian Dinar - DZD).
- External POS terminal or bank card API integration (strictly cash/check clinic register).

## Decisions

### 1. Append-Only Ledger Table (`payment`)
- **Decision**: Create an immutable `payment` table using signed decimal amounts:
  ```sql
  CREATE TABLE IF NOT EXISTS payment (
      id           INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
      patientId    INTEGER NOT NULL REFERENCES patient(id),
      sessionId    INTEGER REFERENCES session(id) ON DELETE SET NULL,
      paymentDate  DATE NOT NULL DEFAULT CURRENT_DATE,
      createdAt    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
      amount       DECIMAL(12,2) NOT NULL CHECK (amount <> 0),
      paymentType  VARCHAR(20) NOT NULL,
      reversalOf   INTEGER REFERENCES payment(id),
      reason       VARCHAR(255),
      createdBy    VARCHAR(50) NOT NULL,
      CONSTRAINT uq_reversal UNIQUE (reversalOf)
  );
  ```
- **Rationale**:
  - `amount > 0`: Inflow (cash into clinic).
  - `amount < 0`: Outflow (refunds to patients or reversals).
  - `uq_reversal`: Guaranteed database-level constraint preventing duplicate reversals of the same entry.
  - `createdBy`: Captures the authenticated user (`UserSession.getCurrentUser().getUserName()`) for auditability.
- **Alternatives Considered**:
  - *Mutable payments table*: Rejected because editing past payments alters historic closed daily registers and destroys audit trails.

### 2. Universal Balance & Cash Register Formulas
- **Decision**:
  - **Patient Balance**:
    $$\text{Balance} = \sum(\text{Session Costs}) + \sum(\text{Therapy Plan Costs}) - \sum(\text{Payment Amounts})$$
    - $\text{Balance} < 0$: Patient has advance credit (e.g. $-1\,500\text{ DA}$).
    - $\text{Balance} > 0$: Patient has debt (e.g. $+500\text{ DA}$).
  - **Daily Cash Register**:
    $$\text{Cash Register} = \sum_{\text{paymentDate} = \text{Target Date}} \text{amount}$$
    Breakdown grouped by `paymentType` shows gross collected, refunds, reversals, and net physical drawer cash.

### 3. Session Form Experience & Transactional Integrity
- **Decision**: In `SessionFormController`:
  - When patient is chosen, check their current balance.
  - Cost field: defaults to treatment cost (e.g. 500 DA).
  - "Cash received today" field:
    - If patient has credit $\ge \text{cost}$: defaults to `0.00`.
    - If patient owes: defaults to remaining balance needed.
    - Worker can enter any custom cash amount.
  - Save operation executes in a single atomic database transaction:
    1. Insert or update `session` record (recording treatment and cost).
    2. If `cashReceived > 0`, insert `payment` row with `sessionId`.
    3. Update `patient.totalCost` and `patient.totalPaid`.

### 4. Patient Search Component (`PatientSearchSelector`)
- **Decision**: Implement a search popover/dropdown filtering on `FilteredList<Patient>`:
  - Match logic: `name.toLowerCase().contains(q) || phone.replace(" ", "").contains(q.replace(" ", ""))`.
  - Row rendering: Patient Name, Phone number, and colored badge (🟢 Avance, 🔴 Dette, ⚪ À jour).
  - Keyboard navigation: Down/Up arrows select items, Enter commits selection, Escape cancels.

### 5. Role-Based Permissions for Financial Operations
- **Decision**:
  - **Employees (`Employé`)**: Record sessions, receive cash, add free deposits (`DEPOSIT`).
  - **Administrators (`Admin`)**: Perform reversals (`REVERSAL`), issue refunds (`REFUND`), and inspect ledger audit logs.

## Risks / Trade-offs

| Risk | Mitigation |
| :--- | :--- |
| **Legacy data corruption during backfill** | Automated pre-migration backup of `clinic.mv.db`. Idempotent `NOT EXISTS` query logic. Parity assertions checking that new balance equals legacy $(totalCost - totalPaid)$. |
| **Accidental double reversal** | Enforced at schema level with `CONSTRAINT uq_reversal UNIQUE (reversalOf)`. |
| **Worker attempts refund larger than credit** | UI and DAO validation strictly disallow `REFUND` if amount exceeds available patient credit. |
| **LAN query latency loading patient search** | Precompute and cache patient balances in `Patient` objects during initial fetch; search filters in-memory via `FilteredList`. |

## Migration Plan

1. **Pre-Migration Safety**: Copy `clinic.mv.db` to `~/clinic/backups/pre_ledger_migration_<timestamp>.mv.db`.
2. **Schema Creation**: Create `payment` table and indexes (`idx_payment_patientId`, `idx_payment_date`).
3. **Session Backfill**: Stream `session` records (`paidAmount > 0`, `therapyPlanId IS NULL`) into `payment` with `paymentType = 'SESSION'`, `createdBy = 'MIGRATION'`.
4. **Therapy Plan Backfill**: Stream `therapyPlan` records (`cost > 0`) into `payment` with `paymentType = 'THERAPY_PLAN'`, `createdBy = 'MIGRATION'`.
5. **Totals Synchronization**: Re-sync `patient.totalCost` and `patient.totalPaid` against the newly populated ledger.
6. **Rollback Strategy**: If any step fails, restore the pre-migration database snapshot.
